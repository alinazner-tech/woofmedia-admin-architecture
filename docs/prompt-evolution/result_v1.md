# Архітектура адмін-панелі WoofMedia (фронтенд) — v1

Документ для двох фронтендерів на пів року роботи. Межі рішення: Next.js 14 (App Router, TypeScript), вісім PHP-сервісів із REST і JWT RS256, які ми не змінюємо, i18n (спершу українська, потім польська). Усе, що я добудував через брак даних, зібрано в розділі 10. Посилання виду «(П3)» ведуть на пункт звідти.

**Головна теза.** Браузер не звертається до PHP-сервісів напряму. Єдиний клієнт бекенду — сервер Next.js. На ньому зосереджено все, що стосується безпеки: сесію, перевірку доступу до рядка, відбір полів за роллю і фільтрацію подій реального часу. Інші рішення в документі випливають із цього.

## 1. Карта модулів

### 1.1. Модулі

| Модуль | Що містить | Для кого |
|---|---|---|
| `server/session` | Шифрована cookie з JWT, перевірка підпису RS256, оновлення токена | інфраструктура |
| `server/access` | Ролі, права, скоуп рядка, гарди | інфраструктура |
| `server/backend` | `backendFetch` і вісім тонких клієнтів сервісів з таймаутами та типізованими помилками | інфраструктура |
| `server/events` | Хаб подій: одне опитування бекенду й розсилка по SSE | інфраструктура |
| `modules/projects` | Черга, картка, чек-лист, нотатки, статусна машина, звіт і приймання | усі ролі, обмеження на рівні рядка |
| `modules/smm` | Календар, редактор постів, статус апруву | за скоупом проєктів (П9) |
| `modules/finance` | MRR, тарифи, churn, ARPU, LTV за когортами, P&L | лише супер-адмін |
| `modules/prompts` | Список, редагування, diff, публікація, історія, відкат | лише супер-адмін |
| `modules/monitoring` | Аптайм, помилки, час відповіді, навантаження | лише супер-адмін |
| `shared/*` | UI-примітиви, i18n, час, клієнт реального часу | усі |

### 1.2. Правила імпорту

```
app/ ──► modules/*/index.ts (лише публічний API модуля)
modules/* ──► shared/*, server/* (server/* — лише з серверних файлів)
modules/smm ──► modules/projects (лише публічний API: тип ProjectRef, <ProjectHeader/>)
shared/* ──► нічого з modules/* і server/*
```

**Межі, заборонені в обидва боки:**

| Пара | Чому |
|---|---|
| `finance` ⇄ будь-який інший модуль у `modules/` | Кожен спільний імпорт — потенційний канал витоку грошових полів у спільний тип або компонент. Фінанси — окремий острів |
| `finance` ⇄ `server/events` | Через SSE не йде жодна подія з грошима. Хаб навіть не знає, що фінанси існують |
| `prompts` ⇄ `projects` | Промпти — конфігурація AI-сервісу. Картка проєкту показує результат роботи AI, який повернув бекенд, і не працює з промптами |
| `monitoring` ⇄ будь-який доменний модуль | Моніторинг читає лише метрики сервісів. Якщо доменні модулі залежатимуть від нього, падіння моніторингу потягне їх за собою |
| будь-який файл із `'use client'` ⇄ `server/*` і `modules/*/server/*` | Код доступу до даних і токени не мають потрапити в бандл. Забезпечується пакетом `server-only`: збірка падає |

`projects → smm` заборонено в один бік. Картка проєкту не імпортує SMM. Якщо SMM-блок потрібен на сторінці проєкту, його компонує маршрут у `app/`.

**Чим забезпечується.** Правилом `no-restricted-imports` з вбудованого ESLint через `overrides` за шляхами: кожна заборона займає кілька рядків, залежність не потрібна. Плюс `import 'server-only'` у першому рядку кожного файлу в `server/` та `modules/*/server/`. `eslint-plugin-boundaries` не беремо: для п'яти модулів він не вартий ще однієї залежності.

## 2. Модель доступу

### 2.1. Ролі, скоуп і права

```ts
type Role = 'specialist' | 'teamlead' | 'super_admin';
interface SessionUser { id: string; role: Role; teamId: string | null; locale: 'uk' | 'pl' }

type Scope =
  | { kind: 'own';  userId: string }   // specialist
  | { kind: 'team'; teamId: string }   // teamlead
  | { kind: 'all' };                   // super_admin

function scopeOf(u: SessionUser): Scope;
function canSeeProject(u: SessionUser, p: { assigneeId: string; teamId: string }): boolean;
```

| Право | Спеціаліст | Тімлід | Супер-адмін |
|---|---|---|---|
| `project:read` | own | team | all |
| `project:checklist`, `project:note` | own | team | all |
| `project:transition` | own, лише переходи спеціаліста | team | all |
| `project:reassign` | — | team | all |
| `project:accept`, `project:return` | — | team | all |
| `project:adAccess` (доступи до кабінетів) | own | team | all (П7) |
| `smm:*` | own (П9) | team (П9) | all |
| `finance:read` | — | — | all |
| `prompts:read`, `prompts:write`, `prompts:publish` | — | — | all |
| `monitoring:read` | — | — | all |

Матриця — це одна константа в `server/access/permissions.ts`. Роль, `id` і `teamId` беремо з JWT, підпис якого перевірено публічним ключем (П2).

### 2.2. Де перевіряється доступ

| Рівень | Що перевіряє | Чи довіряємо |
|---|---|---|
| 0. PHP-сервіси | Роль і власника за JWT | **Припускаю, що перевіряють (П1).** Від цього залежить захист від клієнтів мобільного застосунку, тобто від викликів поза панеллю |
| 1. `middleware.ts` | Лише наявність сесії та оновлення токена | **Ні, для авторизації не використовується.** Middleware можна обійти (див. CVE-2025-29927), і він не бачить рядків |
| 2. Layout `(super)` | Роль супер-адміна | Тільки для UX: не рендерить оболонку. Layout не перерендериться під час клієнтської навігації, тому межею безпеки він не є |
| **3. Рівень доступу до даних (DAL)** | Кожна функція в `modules/*/server/queries.ts` першим рядком викликає гард. Для рядка перевіряє `canSeeProject` | **Так. Це основна точка перевірки** |
| **4. Server Actions і Route Handlers** | Обгортка `authedAction`: сесія, право, zod-схема вводу, доступ до конкретного рядка | **Так.** Кожна Server Action — публічний POST-ендпоінт. Те, що сторінку вже перевірили, не рахується |
| 5. SSE-хаб | Кожну подію фільтрує `canSeeProject` для кожного підписника | **Так**, інакше подія «проєкт X змінив статус» розкриває чужий рядок |

```ts
function requireSession(): Promise<SessionUser>;                  // інакше redirect('/login')
function requirePermission(p: Permission): Promise<SessionUser>;  // інакше notFound()
function getProjectForUser(u: SessionUser, id: string): Promise<ProjectDTO>; // чужий рядок → notFound()

function authedAction<I, O>(
  opts: { permission: Permission; input: ZodType<I>; resource?: (i: I) => { projectId: string } },
  fn: (user: SessionUser, input: I) => Promise<O>
): (input: I) => Promise<ActionResult<O>>;
```

На прямий запит `/projects/123` із чужим проєктом відповідь 404, а не 403, щоб не підтверджувати, що рядок існує. Для списків DAL передає скоуп у запит до бекенду як фільтр (`assignee=me` / `team=X`) і додатково фільтрує результат. Якщо бекенд такого фільтра не має (П1), пагінація за скоупом ламається, і це треба закрити питанням, а не обходити.

**Правило, яке перевіряємо на рев'ю:** у `modules/*/server/` немає експортованої функції, яка повертає дані без виклику гарда в першому рядку. Для цього є юніт-тест: він проходить по експортах і викликає кожен без сесії.

### 2.3. Як фінанси фізично не досягають клієнта спеціаліста

Витекти дані можуть сімома шляхами. Кожен закрито окремо:

1. **Пропси і RSC-пейлоад.** Фінансові запити є лише в `modules/finance/server/`. Кожен викликає `requirePermission('finance:read')` усередині себе, а не в layout. Сторінку спеціаліста відрендерити неможливо, тож пейлоаду немає.
2. **Грошові поля в нефінансових відповідях.** Відповідь сервісу проєктів може містити ціну, тариф клієнта чи виплату. Тому DTO будується за **білим списком** полів для кожної ролі: `toProjectDTO(raw, role)`, окремий тип для кожної ролі. Чорний список не використовуємо: нове поле в бекенді за замовчуванням не проходить.
3. **Кеш Next.js.** У Next 14 `fetch` у RSC за замовчуванням кешується в Data Cache, спільному для всіх користувачів. `backendFetch` жорстко ставить `cache: 'no-store'`, а `(panel)/layout.tsx` оголошує `dynamic = 'force-dynamic'`. `unstable_cache` дозволений лише для довідників, що не залежать від користувача (шаблони чек-листів, словник статусів).
4. **Прямий виклик PHP з токеном зі сторінки.** JWT лежить в httpOnly-cookie, **зашифрованій** (JWE, `jose`). Httponly-cookie видно у вкладці Application девтулзів, але розшифрувати її вміст спеціаліст не може. Тому свого JWT у нього немає, і викликати фінансовий сервіс напряму він не може. Для клієнтів мобільного застосунку, у яких JWT є, захист лише на бекенді (П1).
5. **SSE.** Події несуть тільки `{type, projectId, updatedAt}`. Грошей у схемі подій немає за типом, а імпорт `finance` у хабі заборонено правилом.
6. **Тексти помилок.** Помилки бекенду перетворюються на типізовані коди. Сире тіло відповіді не доходить ні до клієнта, ні в `error.tsx`.
7. **JS-чанки.** Код фінансових графіків — окремий чанк, і теоретично його можна завантажити за прямою адресою. Даних у ньому немає, тому це прийнятно.

**Перевірка:** e2e-тест на Playwright «канарка». У тестових фінансових даних лежить унікальний рядок-маркер. Тест логіниться спеціалістом і тімлідом, обходить усі маршрути, відкриває картку, чекає подію SSE і перевіряє, що маркера немає в жодній відповіді: HTML, RSC-пейлоаді, JSON, потоці SSE. Тест запускається в CI на кожен PR. Він коштує день роботи і, на мою думку, це найцінніший тест у проєкті.

`experimental_taintObjectReference` з React не використовуємо як захист: у Next 14 це експериментальний прапорець. Можна ввімкнути як додатковий рівень, але покладатися на нього не можна.

## 3. Стратегія даних

### 3.1. Напряму чи через прошарок: через прошарок, і цей прошарок — сам сервер Next.js

Окремого сервісу не робимо. Роль BFF виконують RSC, Server Actions і два Route Handlers (SSE і моніторинг).

Обґрунтування за критеріями:
- **Безпека (вимога з задачі).** Відбір полів за роллю, приховування JWT і фільтрацію подій неможливо зробити, якщо браузер ходить у PHP сам. Прямі виклики означають, що JWT у браузері, а тоді пункт 4 з 2.3 не закрити.
- **Ізоляція відмов.** Один `backendFetch` дає таймаут і типізовану помилку для кожного сервісу. Без прошарку вісім сервісів потребували б восьми CORS-конфігурацій і восьми способів падати в браузері.
- **Вартість для двох людей.** Next.js-сервер у нас і так є. Окремий BFF-сервіс (Node або GraphQL) — це ще один деплой, ще один репозиторій контрактів і ще один стек для чергування.

Ціна рішення: кожен запит проходить зайвий хоп, і сервер Next.js стає критичним компонентом. Для кількох десятків співробітників (П10) ні те, ні інше не проблема.

### 3.2. Кешування

| Шар | Політика |
|---|---|
| Data Cache Next.js | Вимкнено для всіх даних користувача (`no-store`). `unstable_cache` з тегом і `revalidate: 600` лише для довідників |
| Дедуплікація в межах одного рендеру | `React.cache()` для `getSession`, `getProjectForUser`: кілька компонентів сторінки роблять один запит |
| Full Route Cache | Вимкнено (`force-dynamic` на `(panel)`) |
| Router Cache (клієнт) | `experimental.staleTimes.dynamic = 0` (Next 14.2+), щоб «назад» не показував застарілий статус |
| Клієнтська бібліотека кешу | Немає (ADR-3) |
| Глобальний стор | Немає. Кандидатів перевірено: тікер SLA — модульний хук; фільтри черги — URL; чернетка нотатки — локальний стан; поточний користувач — пропс із серверного layout. Задачі, яку не закриває серверний кеш, не знайшлося |

### 3.3. Інвалідація після зміни статусу

1. Кнопка переходу викликає Server Action `transitionProject({id, to, expectedStatus})`.
2. Дія перевіряє доступ і робить PATCH у сервіс проєктів з очікуваним поточним статусом. Якщо бекенд повертає конфлікт (П5), дія повертає `{ok:false, code:'conflict'}`, а UI пропонує оновити сторінку.
3. Якщо все пройшло, `revalidatePath('/queue')` і `revalidatePath('/projects/[id]', 'page')`. Поточна вкладка отримує свіжий RSC у тій самій відповіді.
4. Інші вкладки й інші користувачі отримують подію з хаба (розділ 5) і викликають `router.refresh()` з дебаунсом 500 мс, щоб серія подій злилася в одне оновлення. `router.refresh()` зберігає локальний стан клієнтських компонентів, тому недописана нотатка не зникає.

Для чек-листа і статусних кнопок оптимістичний UI робимо через `useOptimistic` з React: це вбудований засіб, без бібліотеки.

### 3.4. Узгодженість між вкладками

У кожної вкладки своє SSE-з'єднання, тож кожна отримує ті самі події з сервера, включно з наслідками змін в іншій вкладці. Окремої синхронізації між вкладками не потрібно. Єдиний виняток — вихід із системи: `BroadcastChannel('woof-session')` повідомляє інші вкладки, і вони переходять на `/login`. Кілька SSE-з'єднань з одного браузера нормальні за HTTP/2 (П11). За HTTP/1.1 ліміт у 6 з'єднань на домен почне заважати з п'ятої вкладки.

## 4. Межа сервер/клієнт

**Критерій.** Компонент клієнтський лише тоді, коли йому потрібне щось із трьох:
- (а) час браузера, тобто щось, що змінюється без запиту: тікер;
- (б) локальний інтерактивний стан, наприклад оптимістичний UI, відкритий діалог чи поле редактора;
- (в) API браузера: `EventSource`, `BroadcastChannel`, `visibilitychange`.

Усе інше серверне, **зокрема все, що торкається даних, залежних від ролі**. Клієнтський компонент отримує тільки DTO, спроєктований як пропс. Сирих відповідей бекенду він не отримує ніколи.

| Сторінка | Серверне | Клієнтське («листя») |
|---|---|---|
| Черга | Таблиця, фільтри (через `searchParams`), сортування | `<SlaBadge>`, `<LiveRefresh>` (підписка SSE), селектор фільтрів |
| Картка | Бриф, чек-лист (розмітка), нотатки (список), історія статусів | `<ChecklistItem>` з `useOptimistic`, два окремі композитори нотаток, `<TransitionButtons>`, `<RevealAdAccess>` |
| Звіт і приймання | Звіт | Форма «підтвердити / повернути з коментарем» |
| Фінанси | Усі розрахунки та таблиці когорт | Лише графіки, які отримують масиви чисел, уже агреговані для супер-адміна |
| Промпти | Список, історія, **diff рахується на сервері** | Редактор (textarea), кнопки публікації та відкату |
| Моніторинг | Первинний знімок | `<MonitoringPoller>` |
| SMM | Календарна сітка, пости | Редактор поста |

Нотатки мають дві окремі Server Actions: `addInternalNote` і `addClientNote`. Одна дія з прапорцем `visibility` не підходить, бо одна помилка в пропсі відкриє внутрішню нотатку клієнту.

Доступи до рекламних кабінетів не входять у пейлоад сторінки. Їх віддає окрема дія `revealAdAccess(projectId)` за кліком, з перевіркою доступу й без кешування (П7).

**Де межа ламається через SLA:**
1. **Колір і лічильник залежать від часу**, тож сервер, який рендерить раз, не може бути їх власником. `<SlaBadge deadlineAt pausedAt>` отримує абсолютні мітки. Сервер віддає `serverNow` у layout, клієнт рахує зсув годинника. Один тікер `setInterval(1000)` на всю сторінку (модульний хук на `useSyncExternalStore`), а не таймер на кожен рядок.
2. **Гідрація.** HTML з сервера зрендерено в інший момент, ніж гідрацію на клієнті, тому текст лічильника розійдеться. Рішення: на сервері бейдж рендерить колір, обчислений за `serverNow`, а цифри лічильника — лише після монтування.
3. **Сортування застаріває.** Якщо сортувати за «залишком часу», порядок з часом стає неправильним. Тому сортуємо за абсолютним `deadlineAt`: цей порядок не залежить від часу. **Але** фільтр «лише прострочені», зроблений на сервері, застаріє: рядок почервоніє, а у відфільтрованому списку не з'явиться до наступного оновлення. Тому такий фільтр рахуємо на клієнті поверх уже завантаженого списку.
4. **Пауза SLA.** Якщо в деяких статусах SLA стоїть на паузі (П4), інваріантність порядку зникає, і сортування має робити бекенд за «ефективним дедлайном».

## 5. Реальний час

Три випадки — три різні відповіді.

| Випадок | Вибір | Обґрунтування |
|---|---|---|
| **SLA-таймери** | **Мережі немає.** Локальний тікер від абсолютного `deadlineAt` | Дедлайн змінюється лише разом зі статусом або переназначенням, і ці події й так приходять (див. нижче). Щосекундний лічильник через мережу — це трафік без нової інформації. Працює, навіть коли бекенд лежить |
| **Зміни статусів** | **SSE** з Route Handler Next.js | Потік однонаправлений: сервер → клієнт. Мутації вже йдуть через Server Actions. `EventSource` вбудований у браузер, сам перепідключається і вміє `Last-Event-ID`, тож бібліотека не потрібна. Вебсокети дали б двонаправленість, яка нам не потрібна, і вимагали б окремого WS-сервера, бо Route Handlers у Next.js WS не тримають |
| **Моніторинг** | **Опитування раз на 30 с**, лише на сторінці моніторингу і лише у видимій вкладці | Метрики агреговані, свіжість 30–60 с достатня, глядачів один-два. SSE тут дав би ту саму свіжість складнішим способом |

**Звідки хаб бере події.** Бекенд змінювати не можна, і невідомо, чи він публікує події (П3). Базовий варіант такий: `server/events/hub.ts` — один цикл на процес. Раз на 5 с він питає сервіс проєктів «що змінилося з моменту T», наприклад через `updated_since`, і розсилає зміни підписникам після фільтра `canSeeProject`. N відкритих вкладок коштують бекенду одного запиту раз на 5 с, а не N. Якщо в бекенду є вебхук чи брокер, хаб підпишеться на нього, а контракт для клієнта не зміниться.

Технічні умови: `runtime = 'nodejs'`, heartbeat-коментар кожні 25 с, заголовок `X-Accel-Buffering: no` для nginx. Потрібен **довгоживучий Node-процес** (П10). На serverless-хостингу з лімітом тривалості функції такий SSE не працює.

Клієнтський бік: `shared/realtime/useProjectEvents(onEvent)` — близько 40 рядків на `EventSource`. Реакція на подію — `router.refresh()` з дебаунсом. Коли з'єднання втрачено довше ніж на 30 с, показуємо плашку «Оновлення призупинено, дані станом на HH:MM».

## 7. ADR

### ADR-1. Next.js-сервер — єдиний клієнт бекенду; JWT у зашифрованій httpOnly-cookie
- **Контекст.** Фінанси не мають потрапляти до спеціаліста навіть через девтулзи. Бекенд змінювати не можна.
- **Рішення.** Браузер не отримує JWT і не знає адрес PHP-сервісів. Логін іде через Route Handler: креденшали передаються в сервіс авторизації, отриманий JWT і refresh-токен шифруються через JWE (`jose`, A256GCM) і кладуться в httpOnly, Secure, SameSite=Lax cookie. Оновлення токена відбувається в middleware, бо з RSC встановлювати cookie не можна.
- **Наслідки.** Сервер Next.js стає критичною ланкою. Розмір cookie — близько 2–3 КБ. Вихід із системи інвалідує лише нашу cookie (П2).
- **Якщо помилилися.** Припустімо, бекенд таки не перевіряє ролі, і клієнтський JWT з мобільного застосунку відкриває фінанси. Тоді фронтенд цього не виправить, і діра — у бекенді, а не в панелі. Панель лишиться коректною. Інший сценарій: cookie не вміщує токени. Тоді переходимо на серверне сховище сесій (Redis), змінюється лише `server/session/`.

### ADR-2. Авторизація на рівні доступу до даних і DTO за білим списком
- **Контекст.** Розмежування має бути на рівні рядка. Layout і middleware ненадійні як межа.
- **Рішення.** Кожна функція в `modules/*/server/` сама викликає гард. Кожна дія загорнута в `authedAction`. Кожна відповідь бекенду перетворюється на рольовий DTO за білим списком.
- **Наслідки.** Трохи дублювання: гард є і в запиті, і в дії. Потрібна дисципліна, яку тримають тест `dal-guards` і тест-канарка.
- **Якщо помилилися.** Якщо гард забули в одній функції, витік потрапить лише в її відповідь, і канарка в CI його зловить. Якщо модель скоупу складніша, ніж «own / team / all» (скажімо, кілька команд у тімліда чи тимчасовий доступ), зміниться лише `scope.ts` і `canSeeProject`.

### ADR-3. Без клієнтської бібліотеки кешу й без глобального стора: RSC, Server Actions і `router.refresh()`
- **Контекст.** Двоє розробників. Більшість екранів — читання з точковими мутаціями.
- **Рішення.** Сервер — єдине джерело правди. Мутації йдуть через Server Actions з `revalidatePath`. Живі оновлення — через подію, після якої викликається `router.refresh()`.
- **Наслідки.** Одна модель даних замість двох (RSC плюс клієнтський кеш). Мінус: `router.refresh()` перерендерює весь сегмент, а не один рядок.
- **Якщо помилилися.** Ознаки: черга з сотнями рядків оновлюється помітно повільно, або редактор промптів чи календар SMM потребують складного клієнтського стану. Тоді додаємо TanStack Query **в один модуль**. Межі модулів і DAL не зміняться, бо Route Handler з тим самим гардом замінить RSC як джерело даних. Вартість — тиждень на модуль.

### ADR-4. SSE із Next.js-процесу з одним опитувачем бекенду
- **Контекст.** Статуси змінюють і клієнт (із застосунку), і спеціаліст. Невідомо, чи бекенд публікує події.
- **Рішення.** Один хаб на процес опитує сервіс проєктів і розсилає події по SSE, фільтруючи їх за доступом.
- **Наслідки.** Потрібен постійний Node-процес і **один інстанс** (стан хаба живе в пам'яті). Затримка подій — до 5 с плюс дебаунс.
- **Якщо помилилися.** Якщо хостинг виявиться serverless, або знадобиться кілька інстансів, або бекенд не вміє «змінене з моменту T», переходимо на опитування з клієнта раз на 15 с (`router.refresh()` за таймером). Клієнтський хук `useProjectEvents` приховує джерело, тож зміна займе день, а навантаження зросте пропорційно кількості вкладок. Кілька інстансів потребуватимуть pub/sub (Redis), і це вже нова інфраструктура.

### ADR-5. Статусна машина належить бекенду, фронтенд лише показує дозволені переходи
- **Контекст.** Вісім станів, частину переходів ініціює клієнт, частину спеціаліст. Бекенд уже валідує переходи (П5).
- **Рішення.** `status-machine.ts` містить тільки мапу «стан → підпис, колір, i18n-ключ» і таблицю «який перехід доступний якій ролі в UI». Якщо бекенд віддає `allowedTransitions` для поточного користувача, кнопки будуються з нього, а локальна таблиця стає лише запасним варіантом. Переходи, які ініціює клієнт, у панелі не мають кнопок. Вони лише приходять подіями.
- **Наслідки.** UI може показати кнопку, яку бекенд відхилить. Це обробляється як звичайна помилка дії.
- **Якщо помилилися.** Якщо в бекенду немає `allowedTransitions`, таблиця дублюється і з часом розходиться з бекендом. Тоді нас рятує контрактний тест: e2e проходить усі пари «стан × роль» на стенді. Найгірший варіант — бекенд не валідує переходи зовсім. Тоді фронтенд-таблиця стає єдиною перевіркою, і її треба перенести в `authedAction` як жорсткий гард, а не лише UI.

## 8. Чого я не обрав і чому

1. **Прямі виклики з браузера до восьми PHP-сервісів**, з токеном у пам'яті та CORS. Відмова: JWT опиняється в браузері, спеціаліст може сам покликати фінансовий сервіс, а відбір полів за роллю зробити ніде. Порушує головну вимогу задачі.
2. **Окремий BFF-сервіс або GraphQL-шлюз.** Відмова: це ще один деплой і схема, яку треба підтримувати двом людям. Усе, що він дає, сервер Next.js уже вміє.
3. **TanStack Query або SWR як основний шар даних.** Відмова: два джерела правди (RSC і клієнтський кеш), дублювання авторизації в Route Handlers під кожен запит і ~13 КБ бандла. Лишається шляхом розширення на рівні одного модуля (ADR-3).
4. **Глобальний стор (Zustand, Redux).** Відмова: жодної задачі, яку не закриває серверний кеш, не знайшлося (див. 3.2).
5. **Вебсокети (socket.io чи власний WS-сервер).** Відмова: для однонаправленого потоку вони надлишкові, до того ж потребують окремого процесу поза Next.js, бібліотеки і ручного перепідключення.
6. **Авторизація в middleware.** Відмова: middleware не бачить рядків, а історія CVE-2025-29927 показала, що його можна обійти.
7. **Auth.js (NextAuth).** Відмова: у нас наявний JWT-сервіс і роль у claims. Credentials-провайдер Auth.js додав би шар абстракції над трьома функціями, які й так потрібні (`encrypt`, `verify`, `refresh`), і залежність, яку доведеться оновлювати разом із мажорними версіями Next.
8. **`next-intl`.** Відмова для старту: у внутрішньої панелі мова береться з профілю, тож локаль у URL і маршрутизація в middleware не потрібні. Для двох мов вистачає власного шару приблизно на 80 рядків: типізовані словники, `Intl.PluralRules` (складні форми множини в українській і польській він покриває), `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat`. Ключі робимо вкладеним JSON-сумісним об'єктом, тому міграція на `next-intl` буде механічною, якщо з'являться ICU-повідомлення чи переклад силами перекладачів.

## 9. Режими відмови

**Принцип.** Оболонка панелі (layout, меню, сесія) не залежить від жодного бекенд-сервісу. JWT перевіряється локально публічним ключем, меню будується з ролі. Тому білого екрана не буде, поки живий сам сервер Next.js.

**Механізм.**
- `backendFetch` має таймаут 5 с на читання і 10 с на запис та повертає `ServiceError{service, code}`.
- Основні дані сторінки (картка, черга) кидають помилку, і її ловить `error.tsx` сегмента, де є кнопка «Спробувати знову» (`reset()`).
- Другорядні секції (історія, SMM-блок, нотатки, якщо вони в іншому сервісі) повертають `Result<T, ServiceError>` і рендерять плашку «Розділ тимчасово недоступний». Кожна секція загорнута у власний `<Suspense>`, тож повільний сервіс не блокує решту сторінки.

Конкретна прив'язка функцій до сервісів невідома (П6). Таблиця складена за функцією:

| Лежить | Що бачить користувач | Що працює |
|---|---|---|
| Авторизація | Нові логіни: «Вхід тимчасово недоступний». Наявні сесії працюють до спливу access-токена, потім людину перекидає на логін із тим самим повідомленням | Усе, поки токен дійсний |
| Проєкти | Черга і картка: блок помилки з повтором. SSE-хаб не отримує змін, у клієнтів з'являється плашка «Оновлення призупинено» | SLA-таймери на вже завантажених сторінках тікають далі. Фінанси, промпти, моніторинг, SMM (якщо це окремий сервіс) |
| Чек-листи або нотатки (якщо окремі) | Секція картки з плашкою, решта картки доступна. Відмітки чек-листа відкочуються з повідомленням | Статуси, бриф, звіт |
| Фінанси | Фінансова сторінка: помилка з повтором, окремо по кожному віджету (MRR, когорти, P&L) | Усе інше |
| AI / промпти | Редактор недоступний. **Незбережений текст промпту лишається в полі.** Дія повертає помилку, стан форми не скидається | Усе інше |
| SMM | Календар: помилка. Картка проєкту без SMM-блоку | Усе інше |
| Метрики моніторингу | Картки сервісів «Немає даних з HH:MM», показуємо останній знімок | Усе інше |
| Сервер Next.js | Білий екран неминучий: це єдина точка, яку панель не може деградувати сама | — |

**Мутації під час відмови.** Жодна дія не очищає форму до успішної відповіді. Для довгих текстів (нотатка, пост, промпт) незбережена чернетка лишається в стані компонента. У `localStorage` її не зберігаємо, бо в ній можуть бути дані клієнта (П12).

## 10. Припущення, суперечності, питання

### 10.1. Припущення (добудовано мною)

- **П1.** PHP-сервіси самі перевіряють роль і власника рядка за JWT і приймають фільтри `assignee`/`team` у списках. Якщо ні, захист від викликів поза панеллю (наприклад, з JWT клієнта мобільного застосунку) фронтенд забезпечити не може.
- **П2.** JWT містить `sub`, `role`, `team_id`, `exp`, а публічний ключ доступний через JWKS або конфіг. Access-токен короткий (≤15 хв), є refresh-токен. Відкликати сесію на бекенді ми не можемо, тому зміна ролі діє після спливу токена.
- **П3.** Бекенд не публікує події, але сервіс проєктів уміє повертати «змінене після T».
- **П4.** SLA — це абсолютний дедлайн без пауз. Пороги: жовтий < 3 год, червоний — прострочено.
- **П5.** Бекенд валідує переходи статусів і підтримує оптимістичне блокування (версія або очікуваний статус).
- **П6.** Відповідність «функція → сервіс» невідома. Таблицю режимів відмови складено за функцією.
- **П7.** Доступи до рекламних кабінетів — секрети, які бекенд віддає окремим запитом.
- **П8.** Промпт — це текст із плейсхолдерами, без структури. Версії незмінні, а відкат означає публікацію старої версії як нової.
- **П9.** SMM-контент належить проєкту, тому доступ визначає скоуп проєкту. Апрув від клієнта відбувається в мобільному застосунку, а панель лише показує його статус.
- **П10.** Користувачів — десятки, а не тисячі. Хостинг — постійний Node-процес в одному інстансі.
- **П11.** Панель віддається через HTTP/2.
- **П12.** Дані клієнтів вважаються чутливими, тож у браузерному сховищі не зберігаються.
- Тімлід має рівно одну команду. Тімлід не бачить фінансів, промптів і моніторингу.

### 10.2. Суперечності у вимогах

1. «Сервер не має віддати чужий рядок» і водночас «бекенд не змінюємо». Панель гарантує це для своїх відповідей. Для відповідей самих PHP-сервісів гарантія на фронтенді неможлива, і вона або вже є, або це задача бекенду.
2. «Спеціаліст фінансів не бачить взагалі», але картка проєкту природно містить ціну, тариф клієнта чи бюджет на рекламу. Незрозуміло, чи **рекламний бюджет у кабінеті** — це фінанси. Без нього спеціалісту важко працювати з кабінетом. Поки що вважаю, що в картці спеціаліста немає жодної грошової величини.
3. У таблиці ролей SMM-модуль не згадано, хоча він входить у перелік функцій панелі. Хто працює з календарем, невідомо.
4. «Лічильник іде в реальному часі», тоді як єдине живе джерело — опитування бекенду з кроком до 5 с. Цифри таймера реальні, а статуси оновлюються з затримкою в секунди.

### 10.3. Питання до людей

1. Чи перевіряють PHP-сервіси роль і власника рядка самостійно? Чи є фільтри за виконавцем і командою у списку проєктів?
2. Які claims у JWT? Який строк життя access- і refresh-токена? Чи є ендпоінт відкликання?
3. Чи вміє бекенд віддавати події (вебхук, брокер, «змінене після T»)? Якщо нічого з цього немає, ADR-4 треба переглянути.
4. Де розгортається панель: власний Node-сервер/контейнер чи serverless? Скільки інстансів?
5. Список восьми станів і хто ініціює кожен перехід. Чи віддає бекенд `allowedTransitions`?
6. Чи зупиняється SLA в якихось станах (наприклад, «чекаємо клієнта»)?
7. Які вісім сервісів і за що відповідає кожен?
8. Чи бачить спеціаліст бюджет рекламного кабінету, ціну проєкту чи тариф клієнта?
9. Хто з ролей працює з SMM-модулем?
10. Чи потрібен аудит-лог перегляду доступів до кабінетів? Чи веде його бекенд?
11. Звідки беруться метрики моніторингу: `/health` кожного сервісу, Prometheus, щось інше? Що означає «навантаження»?
12. Чи можуть кілька супер-адмінів одночасно редагувати один промпт? Чи є на бекенді блокування версій?
13. Чи потрібна чек-листу умова «усі пункти виконано» перед переходом на приймання, і хто її перевіряє?
14. Скільки співробітників і скільки проєктів у черзі одночасно (порядок величини)?

### 10.4. Про вже прийняті рішення (один абзац)

Next.js 14 я б переглянув. У 14-й версії `fetch` у RSC за замовчуванням кешується в Data Cache, спільному для всіх користувачів. Для панелі з розмежуванням на рівні рядка це небезпечне значення за замовчуванням: одна забута `no-store` означає, що чужі дані віддаються з кешу. Тому весь розділ 2.3 п.3 існує лише для того, щоб його компенсувати. У 15-й версії цю поведінку змінено на «не кешувати». Крім того, 14-та гілка вже не отримує нових можливостей, а міграція з 14 на 15 через рік коштуватиме більше, ніж старт одразу на 15. У межах заданого проєктую під 14, а небезпечне значення за замовчуванням закриваю єдиною обгорткою `backendFetch` і лінт-правилом, що забороняє голий `fetch` у `server/` і `modules/*/server/`.
