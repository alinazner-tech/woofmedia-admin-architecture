# Архітектура фронтенду адмін-панелі WoofMedia (v4)

Критерії, проти яких зроблено кожен вибір:

- **К1** – тижні роботи й супроводу для двох людей.
- **К2** – правило перетворюється на автотест.
- **К3** – безпека даних не залежить від фронтенду.
- **К4** – деградація частинами.
- **К5** – мінімум залежностей на три роки.

**[НЕ ЗАХИСТ]** позначає місця, де фронтенд лише приховує. Безпеку там дає тільки сервер: вимога в Додатку А, тест на стенді в Додатку Б.

Твердження про інструменти перевірено на Vite 8.3.1, React Router 8.4.0, TanStack Query 5.104.0, oxlint 1.85.0 (`node_modules` прототипу `woof-admin/`). Це умова перевірки, а не зафіксовані версії.

---

## 1. Карта модулів

| Шар | Зміст | Ролі |
|---|---|---|
| `app` | оболонка, маршрути, провайдери, кореневі межі помилок | усі |
| `platform` | HTTP, сесія, `can()`, годинник, i18n, UI-примітиви | усі |
| `contract` | схеми, коди помилок; фікстури й сценарії – тільки для тестів | – |
| `modules/projects` | черга, SLA, картка, статуси, чек-лист, нотатки, звіт, приймання, переназначення | усі |
| `modules/prompts`, `monitoring`, `finance` | відповідні розділи | супер-адмін |
| `modules/smm` | не створюється (розділ 7) | – |

**Дозволені імпорти:**

- `app` → `platform`, `contract`, `modules/*/index.ts`. `projects` – статично. `finance`, `prompts`, `monitoring` – **тільки** `import()` усередині маршрутного `lazy`.
- `modules/*` → `platform`, `contract` без фікстур.
- `platform` → `contract/common`, ніколи `app` чи `modules`.
- `contract/fixtures`, `contract/scenarios` → лише з `mocks/` і `tests/`.

**Заборонено в обидва боки:** будь-яка пара доменних модулів. `projects → finance` втягне фінанси в бандл спеціаліста. `finance → projects` звʼяже релізи: зміна картки зламає фінанси. Одне правило простіше за матрицю винятків (К1). Спільне без доменного змісту спускається в `platform`, решта дублюється. Наприклад, назву проєкту фінанси беруть зі своєї відповіді.

**Як примусити:**

1. `no-restricted-imports` з `overrides` для кожної теки. В oxlint 1.85 правило має `patterns`, конфіг – `overrides` за glob (перевірено за схемою). Лінтер у поточному шаблоні `create-vite` **не перевірено**: якщо там ESLint, беремо його базове правило, другий лінтер не додаємо.
2. `scripts/check-role-chunks.ts` (близько 30 рядків) після збірки з `build.manifest: true`. Проходить статичні `imports` від точки входу і падає, якщо досяжний чанк із `src` у `modules/{finance,prompts,monitoring}`. Лінтер ловить прямий імпорт, скрипт – транзитивний. Поля `imports`, `src`, `isEntry` перевірено в типах Vite 8.3.1.

## 2. Модель доступу

Права – з `GET /me` (А-6). JWT фронтенд не декодує: джерело одне, серверне (К3).

| Право | Спеціаліст | Тімлід | Супер-адмін |
|---|---|---|---|
| `project.view` (обсяг визначає сервер) | призначені | своя команда | усі |
| `project.transition` (конкретні переходи – з сервера) | так | так | так |
| `project.reassign`, `project.accept` | – | своя команда | усі (П10) |
| `project.adAccess.view` | призначені | своя команда (П10) | усі |
| `note.write.internal`, `note.write.client` | так | так | так |
| `prompts.edit`, `prompts.publish` | – | – | так |
| `monitoring.view` | – | – | так |
| `finance.view` | – | – | так |

**Де перевіряється кожне правило:**

| Правило | Дані (сервер – єдиний гарант) | Код (збірка, завантаження) | Інтерфейс |
|---|---|---|---|
| Бачити проєкт | список обмежено обсягом ролі; чужий id повертає 404 (А-7) | – | черга показує рівно те, що прийшло; фронтенд нічого не фільтрує |
| Змінити статус | роль, поточний стан, коментар, версія (А-10…А-13) | – | кнопки лише з `availableTransitions` **[НЕ ЗАХИСТ]** |
| Переназначити, прийняти | роль і команда (А-14) | – | кнопки за `can()` **[НЕ ЗАХИСТ]** |
| Фінанси | 403 на `/finance/*`; у DTO проєкту для не-супер-адміна **немає** фінансових полів (А-8, А-9) | `lazy`, заборона імпорту, перевірка маніфесту | охоронець маршруту, пункт меню **[НЕ ЗАХИСТ]** |
| Промпти, моніторинг | 403 на префікси (А-8) | те саме | те саме **[НЕ ЗАХИСТ]** |
| Внутрішня нотатка | обовʼязкове поле `visibility`; клієнтське API внутрішніх нотаток не віддає (А-15) | – | за замовчуванням «внутрішня» **[НЕ ЗАХИСТ]** |
| Доступи до кабінетів | окремий ендпоїнт, лише за правом, з аудитом (А-16) | – | показ на вимогу, не кешується **[НЕ ЗАХИСТ]** |

**Охоронець.** У React Router 8.4.0 `lazy` виконується паралельно з лоадерами (перевірено в `router.js`), тож перевірка в лоадері **не** зупинить завантаження чанка. Перевірка стоїть усередині `lazy`:

```ts
lazy: async () => {
  const me = await ensureMe(queryClient);          // /me з кешу або з мережі
  if (!can(me, 'finance.view')) return { Component: Forbidden };
  return import('../modules/finance/routes');
}
```

Це гігієна, а не безпека: чанки лежать на CloudFront публічно, код не секрет (К3).

## 4. Стратегія даних

**Серверний кеш – TanStack Query, і тільки він (ADR-1).** `staleTime` 30 с для списків, 0 для картки. `retry` 1 для 5xx і мережі, 0 для 4xx. `refetchOnWindowFocus: true`. Персистера немає (розділ 12). Ключі – фабрика в модулі: `projectKeys.lists()`, `.list(f)`, `.detail(id)`, `.history(id)`, `.adAccess(id)`.

**Валідація.** Відповіді проходять схему в `platform/http`. Розбіжність – помилка `CONTRACT_MISMATCH` одного блоку, не сторінки (К4). Невідомі поля відкидаються, змінений тип ламає – так і має бути.

**Після зміни статусу:** відповідь переходу – оновлена картка (А-12) → `setQueryData(detail)` → `invalidateQueries(lists(), history(id))` → повідомлення `invalidate` іншим вкладкам.

Оптимістичних переходів немає: сервер відмовляє з причин, яких фронтенд не бачить (клієнт уже змінив статус), а відкат статусу на очах гірший за 300 мс очікування. Оптимістично – лише позначки чек-листа, з відкатом.

**Одночасні зміни.** Перехід несе `expectedVersion`; 409 `STALE_VERSION` → перечитати картку, показати «проєкт щойно змінився» (А-13).

**Вкладки одного користувача.** Власний `BroadcastChannel`, близько 25 рядків: `invalidate {keys}` і `session {kind, userId}`. Лише ключі й ідентифікатори, ніколи дані. Загублене повідомлення страхує `refetchOnWindowFocus`. Плагін синхронізації кешу TanStack Query не беру: синхронізує весь кеш, а нам досить інвалідації; статус «експериментальний» не перевірено (П13).

**Глобального стору немає.** Фільтри черги – у URL. Модалки й чернетки – `useState`. Сесія – запит `['me']`. Годинник SLA – `useSyncExternalStore` у `platform/realtime/clock.ts` (близько 15 рядків). Задачі, якої не розвʼязує серверний кеш, не знайдено; перший кандидат – чернетки SMM, модуль відкладено.

## 5. Реальний час

| Випадок | Механізм | Чому |
|---|---|---|
| SLA-лічильник | **без сервера**: від `deadline` і зсуву годинника | Дедлайн відомий; його зміна приходить разом зі зміною проєкту |
| Зміна статусу | **опитування** курсора раз на 20 с у видимій вкладці + при фокусі | Затримку ніхто не назвав (П5). SSE на PHP коштує більше, ніж дає |
| Моніторинг | **опитування** раз на 30 с | Метрики агреговані за інтервалами, дивиться одна людина |

**SLA.** Чиста функція `slaLevel(deadlineMs, nowMs)`, `remaining = deadlineMs − nowMs`:

- `remaining < 0` → червоний (рівно 0 – жовтий, П2);
- `remaining < 10 800 000` (строго менше 3:00:00) → жовтий;
- інакше зелений; рівно 3:00:00 – зелений.

`nowMs = Date.now() + serverOffset`, зсув – із заголовка `Date` відповідей (А-19): годинник спеціаліста може відставати на хвилини, а межа секундна. Відображення відкидає дробові секунди, тож 2:59:59.9 – це «2:59:59» жовтим, цифри не суперечать кольору. Один спільний таймер раз на секунду, лише у видимій вкладці; на `visibilitychange` – негайний перерахунок.

**Статуси.** `GET /projects/changes?since=<cursor>` → змінені id і новий курсор (А-17); інвалідуються їхні `detail` і всі `lists`. 30 користувачів (П4) – 90 запитів на хвилину.

**Моніторинг.** `GET /monitoring/services` не повинен залежати від сервісів, які моніторить (А-18), інакше ляже разом із ними.

## 7. Черговість

Ємність: 2 людини × 26 тижнів ≈ 52 людино-тижні, мінус приблизно 20% на рев'ю, баги й деплой ≈ 40.

**Реліз 1 (тижні 1–15, близько 28 л-т): робоче місце команди.**

| Що | л-т |
|---|---|
| Платформа: сесія, HTTP, межі помилок, i18n (uk), контракт + фейковий бекенд, CI-перевірки меж і чанків | 9 |
| Черга + SLA | 4 |
| Картка: бриф, доступи, чек-лист, нотатки | 6 |
| Статусна машина з коментарями | 4 |
| Фінальний звіт і приймання | 3 |
| Переназначення | 2 |

Цінність: цим щодня користуються всі три ролі; без черги й картки робочого місця немає. Платформа дорога, але без неї кожен наступний модуль коштує вдвічі.

**Реліз 2 (тижні 16–24, близько 12 л-т):**

1. **Промпти** (4). Одна роль, але прямо впливає на якість роботи AI для клієнтів; бекенд імовірно простий.
2. **Моніторинг** (3). Якщо вже є CloudWatch чи Grafana (питання 8) – посилання замість модуля.
3. **Фінанси** (5). Потрібні визначення метрик і агрегації на бекенді (питання 9); одна людина тим часом бере цифри з інших джерел.

Тижні 25–26 – буфер.

**Відкладено:** SMM – найбільший і найменш визначений обсяг, апрув залежить від чужого продукту (мобільного застосунку). Польські тексти – коли назвуть дату; інфраструктура i18n є з релізу 1.

## 8. П'ять ADR

### ADR-1. Серверний кеш – єдине сховище серверних даних

- **Контекст.** Майже весь стан – дані восьми сервісів; двоє розробників.
- **Рішення.** TanStack Query; стан інтерфейсу – в URL і компонентах; глобального стору немає.
- **Наслідки.** Одна модель інвалідації; вихід – це `queryClient.clear()`; немає двох копій даних.
- **Якщо помилилися** (з'явиться складний клієнтський стан, як-от чернетки SMM): локальний стор **у межах одного модуля**, кеш не чіпаємо. Тиждень.

### ADR-2. Доступні переходи статусу приходять із сервера

- **Контекст.** Вісім станів, три ініціатори, частина переходів вимагає коментаря, і інтерфейс має знати це до запиту. Логіка вже живе в PHP.
- **Рішення.** Картка містить `availableTransitions: {to, requiresComment, commentMinLength?}[]` для поточного користувача (А-10). Фронтенд показує тільки їх і блокує відправку без коментаря. Копії автомата у фронтенді немає.
- **Наслідки.** Одне джерело правди; зміна правил не вимагає релізу фронтенду; тести – на фікстурах із різними наборами.
- **Якщо помилилися** (бекенд не може віддавати список): статична таблиця в `contract/transitions.ts`, а тест на стенді перебирає всі «роль × стан × перехід». Два тижні й постійний ризик розсинхрону.

### ADR-3. Контракт – один виконуваний артефакт у репозиторії фронтенду

- **Контекст.** Моки й контракт не мають розійтися; OpenAPI, імовірно, немає (П8).
- **Рішення.** `src/contract` – схеми, коди помилок, фікстури, сценарії доступу. Звідти: типи TypeScript; валідатор відповідей у проді; фейковий бекенд для MSW, що застосовує ті самі сценарії й відмовляє так, як мав би сервер; набір `tests/stand`, що проганяє ті самі сценарії проти стенду з користувачами трьох ролей.
- **Наслідки.** Вимога бекенду закрита, коли зелений її тест на стенді. Моки не знають більше за контракт.
- **Якщо помилилися** (бекенд захоче OpenAPI як джерело): схеми генеруються з OpenAPI, сценарії й фейковий бекенд лишаються. Тиждень.

### ADR-4. Реальний час без постійних з'єднань у релізі 1

- **Контекст.** PHP (П6), статичний фронтенд, вимог до затримки немає.
- **Рішення.** SLA локально; статуси – курсор раз на 20 с; моніторинг – раз на 30 с.
- **Наслідки.** Нової інфраструктури немає; затримка до 20 с; навантаження лінійне від кількості вкладок.
- **Якщо помилилися** (потрібні секунди або опитування навантажує): SSE з того ж курсора через шлюз. Міняється лише `useChangesFeed`. Тиждень для фронтенду, для бекенду – невідомо.

### ADR-5. Токени й кеш тільки в пам'яті вкладки

- **Контекст.** За одним комп'ютером працюють різні люди; дані попереднього не мають пережити зміну сесії.
- **Рішення.** Access-токен – у змінній модуля; refresh – cookie `HttpOnly; Secure; SameSite=Strict` (А-2); кеш не персиститься; у `localStorage` – лише мова.
- **Наслідки.** Перезавантаження = тихий refresh і секунда завантаження. XSS не прочитає refresh-токен. Одночасні refresh різних вкладок серіалізуються через `navigator.locks` (П13), інакше ротація дасть гонку.
- **Якщо помилилися** (cookie на тому ж домені неможлива, П7): refresh у `sessionStorage`, обов'язковий CSP і явне рішення про ризик XSS. Кілька днів.

## 9. Чого я не обрав і чому

1. **Глобальний стор (Redux Toolkit, Zustand).** Задачі для нього немає (розділ 4); друга копія даних – ручна синхронізація й окреме очищення при виході (К1, К5).
2. **Клієнтська копія статусної машини (XState чи таблиця).** Дублює PHP і розходиться з ним; «знати до запиту» закриває `availableTransitions` (ADR-2, К2).
3. **Вебсокети.** Двосторонній канал не потрібен. Потрібні процес для з'єднань, підтримка в шлюзі, перепідключення – заради затримки, якої ніхто не вимагав (К1).
4. **SSE в релізі 1.** На PHP у FPM-моделі з'єднання тримає воркер (П6), плюс шлюз і таймаути. Відкладено, не відкинуто (ADR-4).
5. **OpenAPI з кодогенерацією як джерело.** Специфікації немає (П8), а згенеровані моки не несуть правил «роль × ресурс» – головного, що ми тестуємо (К2).
6. **Персистентний кеш (IndexedDB).** Дані переживали б вихід (К3).
7. **i18next.** Дві мови й `Intl` проти бібліотеки з плагінами (К5).
8. **TanStack Router.** Типізовані маршрути – реальна перевага, але це друга нова модель поруч із Query; `lazy` з охоронцем закриває головне (К1).
9. **Monaco для diff.** Мегабайти заради одного екрана одного користувача (К5).

## 10. Режими відмови

**Принцип.** Кожен блок – свій запит і своя межа `ModuleBoundary`. Оболонка залежить тільки від `/me` у кеші. Недоступний сервіс – 503 з полем `service` (А-5); блок показує «Сервіс недоступний, повторити» і час останніх даних, мутації в ньому вимкнено.

Відповідність восьми сервісів блокам невідома (питання 7), тому таблиця за функціями:

| Що лежить | Що бачить користувач |
|---|---|
| Вхід | Сесія працює до кінця життя access-токена. Refresh отримує 503, **не** 401 (А-4): виходу немає, банер «Вхід тимчасово недоступний», повтор з наростаючою паузою |
| Проєкти | Черга – блок помилки з повтором; решта розділів працює |
| Сервіс блоку картки | Картка відкривається, недоступний блок – з помилкою; залежні переходи сервер відхилить, інтерфейс покаже причину |
| Фінанси, промпти, моніторинг | Лише свій розділ |
| Шлюз цілком | Банер «Немає зв'язку»; дані в пам'яті видно з позначкою часу; мутації вимкнено |
| Відповідь не за схемою | Блок з `CONTRACT_MISMATCH` |

**Збій завантаження чанка** (перевірено на Vite 8.3.1 і React Router 8.4.0):

- Vite кидає на `window` подію `vite:preloadError`. Її `preventDefault()` **ковтає** помилку, і імпорт повертає `undefined`. Тому `preventDefault()` – лише разом із негайним перезавантаженням; прапорець у `sessionStorage` не дає зациклитися.
- Відмова `lazy` рендериться найближчою межею **вище**: власний `ErrorBoundary` модуля лежить у чанку, що не завантажився. Межа статично оголошена на батьківському маршруті в `app/shell`.
- React Router кешує проміс `lazy`, **включно з відхиленим**, тож «повторити» робить `location.reload()`, а не навігацію.
- Скрипт деплою не видаляє старі хешовані файли з S3 щонайменше 7 днів.

`RootBoundary` – остання лінія: сторінка з кнопкою перезавантаження замість білого екрана.

## 12. Межі сесії

Поза пам'яттю вкладки лежать лише refresh-cookie, мова в `localStorage` і прапорець збою чанка в `sessionStorage`. Відповіді API – `Cache-Control: no-store` (А-3), щоб не лишалось і дискового кешу.

**Епоха сесії.** `platform/http/epoch.ts` – лічильник, що росте при кожному вході й виході. Відповідь на запит із попередньої епохи відкидається; інакше запит, що летів під час виходу, поклав би дані попереднього користувача в очищений кеш.

| Перехід | Що відбувається |
|---|---|
| **Вхід** | `clear()`, епоха +1, `/me`, іншим вкладкам – `login {userId}` |
| **Вихід** | `POST /auth/logout` (відкликає refresh), токен обнуляється, `cancelQueries` + `clear()`, епоха +1, `logout` іншим вкладкам, `location.replace('/login')` – повне перезавантаження скидає пам'ять. Інші вкладки роблять те саме |
| **Зміна користувача** | B входить у вкладці 2, вкладка 1 відкрита під A: вкладка 1 отримує `login {userId: B}` і очищується з перезавантаженням. Якщо повідомлення загубилося, відповідь refresh містить `userId` (А-2), і розбіжність дає те саме. Сторінка з back/forward cache (`pageshow`, `persisted`) перевіряє сесію refresh-ем до показу даних |
| **Відкликання прав** | 403 `PERMISSIONS_CHANGED` → повторний `/me`; змінилися роль чи `permissionsVersion` → `clear()` і головна. Уже завантажений чанк лишається до перезавантаження, але даних не отримає. 401 → сценарій виходу. `/me` перечитується і при фокусі |

Вікно, поки діють старі права, визначає бекенд: TTL токена плюс перевірка відкликання (А-4). Фронтенд його не закриває і не вдає, що закриває. У звіти про помилки не потрапляють тіла відповідей.

## 13. Припущення, суперечності, питання

### Припущення

- **П1.** Назви восьми станів невідомі. Тип стану виводиться з контракту, коли їх назвуть.
- **П2.** При рівно 0 до дедлайну – жовтий. Червоний – строго після дедлайну.
- **П3.** SLA не ставиться на паузу в жодному статусі.
- **П4.** Одночасно відкритих панелей до 30.
- **П5.** Затримка появи зміни статусу до 20–30 с прийнятна.
- **П6.** PHP працює в моделі «процес на запит» (FPM чи подібне).
- **П7.** Фронтенд і API на одному сайті (CloudFront, шлях `/api`). Від цього залежить `SameSite=Strict`.
- **П8.** OpenAPI-специфікації немає.
- **П9.** Склад чек-листа для типу проєкту віддає сервер. У фронтенді його немає.
- **П10.** Супер-адмін може все, що тімлід, у всіх командах.
- **П11.** «Повернути на доопрацювання» – звичайний перехід статусу з `requiresComment`.
- **П12.** У черзі одного користувача до кількох сотень проєктів. Віртуалізація не потрібна.
- **П13.** Твердження про інструменти, які я **не** перевірив:
  - лінтер у поточному шаблоні `create-vite`;
  - статус «експериментальний» у плагіна синхронізації кешу TanStack Query;
  - розміри бандлів бібліотек;
  - підтримка `BroadcastChannel` і `navigator.locks` у браузерах команди;
  - чи кладе Chrome у bfcache сторінки з `no-store` (обробник `pageshow` працює в обох випадках).

  Перевірено на версіях зі вступу: подію `vite:preloadError` і її `preventDefault`; поля маніфесту Vite; паралельність `lazy` і лоадерів; кешування відхиленого `lazy`; `no-restricted-imports` з `patterns` і `overrides` в oxlint.

### Суперечності у вимогах

1. **«Строго менше трьох годин – жовтий, прострочено – червоний»** не визначає момент рівно 0. Прийнято П2, потрібне рішення (питання 1).
2. **«Лічильник може не потребувати сервера» і точність до секунди на межі 3:00:00.** Без серверного часу межа залежить від годинника на компʼютері спеціаліста. Розв'язано зсувом годинника, але це вже вимога до сервера (А-19).
3. **«Апрув від клієнта» в SMM і «мобільний застосунок – не твоя зона».** Панель може лише показати статус апруву. Сам апрув – робота іншого продукту. Звідси відкладення.
4. **«Контракт – вимоги фронтенду» і «ти не проєктуєш бекенд».** Контракт у репозиторії фронтенду фактично фіксує форму API. Розв'язано так: форму відповіді бекенд може змінити, а вимоги доступу – ні. Остаточна приймальна перевірка – тести на стенді (питання 14).
5. **Переходи, які ініціює клієнт,** мають відображатися в панелі, але невідомо, чи може персонал виконати їх за клієнта (питання 4).

### Питання

1. При рівно 0 до дедлайну колір жовтий чи червоний?
2. Чи ставиться SLA на паузу в статусах очікування клієнта?
3. Список восьми станів: хто ініціює кожен перехід, які переходи вимагають коментаря?
4. Чи може персонал виконати перехід, який зазвичай ініціює клієнт (наприклад, коли клієнт відповів телефоном)?
5. Що таке «доступи до рекламних кабінетів»: паролі чи запрошення в кабінет? Чи потрібен аудит переглядів?
6. Яка максимальна прийнятна затримка появи зміни статусу?
7. Які з восьми сервісів обслуговують які блоки картки? Хто віддає дані моніторингу?
8. Чи є вже CloudWatch, Grafana чи інший моніторинг?
9. Як визначено churn, ARPU, LTV (період, формула)? Чи рахує їх бекенд?
10. Куди фронтенд відправляє свої помилки: є Sentry чи аналог?
11. Чи може шлюз ставити `HttpOnly` refresh-cookie на домені панелі? Який TTL access-токена? Чи перевіряє шлюз відкликання на кожен запит?
12. Чи блокує незавершений чек-лист якісь переходи?
13. Коли потрібна польська?
14. Чи згоден бекенд, що приймальний критерій вимоги – зелений тест у `tests/stand`?
15. Чи може одна людина бути одночасно тімлідом і спеціалістом на конкретних проєктах?

## Незгода з ухваленими рішеннями

Жодне з ухвалених рішень я не вважаю помилковим. SPA на S3 за CloudFront для панелі за логіном – правильний вибір за вартістю. Одне застереження до «деплой – статичні файли, як решта статики»: наш деплой не може просто синхронізувати теку з видаленням. Старі хешовані чанки мають жити після релізу, а `index.html` – віддаватися з коротким кешем. Інакше кожен реліз посеред робочого дня ламатиме навігацію відкритим вкладкам. Рішення не змінюється, але до скрипта деплою додаються дві вимоги.

## Додаток А. Контракт до бекенду

Кожна вимога – окремий пункт. Колонка «Тест» – ідентифікатор сценарію в `src/contract/scenarios`, що виконується в `tests/stand`. Де написано «шлюз», перевірка має бути до того, як запит дійде до сервісу. Де написано «сервіс», фронтенду байдуже, хто саме перевіряє, аби відповідь була такою.

### Загальне

| № | Вимога | Хто | Тест |
|---|---|---|---|
| А-1 | Кожен запит, крім `/auth/login` і `/auth/refresh`, перевіряється: підпис RS256, `exp`, `iss`, `aud`. Без валідного токена – 401 `TOKEN_INVALID` або `TOKEN_EXPIRED` | шлюз | `auth.no-token`, `auth.expired` |
| А-2 | `POST /auth/login` і `POST /auth/refresh` повертають `{accessToken, expiresIn, userId}` і ставлять refresh-cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`. Refresh ротується. `POST /auth/logout` відкликає refresh | сервіс входу | `auth.refresh-rotates`, `auth.logout-revokes` |
| А-3 | Усі відповіді API: `Cache-Control: no-store` | шлюз | `headers.no-store` |
| А-4 | Відкликання прав: протягом узгодженого вікна після зміни ролі запит зі старим токеном отримує 403 `PERMISSIONS_CHANGED` або 401. Недоступність сервісу входу – 503, ніколи 401 | шлюз | `auth.role-changed`, `auth.service-down-is-503` |

Коди: `TOKEN_INVALID`, `TOKEN_EXPIRED`, `PERMISSIONS_CHANGED`, `FORBIDDEN`, `NOT_FOUND`, `TRANSITION_NOT_ALLOWED`, `COMMENT_REQUIRED`, `STALE_VERSION`, `VALIDATION_FAILED`, `SERVICE_UNAVAILABLE`. ### Деградація

| № | Інваріант | Критерій приймання (автотест) | Де |

| І-20 | Падіння одного сервісу не кладе сторінку | Моки: для кожного сервісу по черзі 503 з `service`. Меню видно. Недоступний блок показує помилку з повтором. Інші блоки відрендерені. Кореневої помилки немає | ФБ (e2e) |
